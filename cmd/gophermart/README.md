# Gophermart: накопительная система лояльности

Целевая версия модуля — Go 1.26.0. По указанию пользователя локальные команды
и проверки выполняются доступным Go 1.27.1; совместимость с Go 1.26 ещё не проверена.

Приложение читает конфигурацию, пишет production JSON-логи уровня info в stderr,
проверяет подключение к PostgreSQL, применяет встроенные SQL-миграции, затем
запускает HTTP-сервер. Реализованы POST `/api/user/register` и POST `/api/user/login`.
Также реализованы защищённые POST и GET `/api/user/orders`, GET `/api/user/balance`
и один последовательный worker начислений. Реализованы списание баллов и история списаний.

## Конфигурация

| Флаг | Окружение | Значение по умолчанию |
| --- | --- | --- |
| `-a` | `RUN_ADDRESS` | `:8080` |
| `-d` | `DATABASE_URI` | обязательно |
| `-r` | `ACCRUAL_SYSTEM_ADDRESS` | обязательно |
| нет | `JWT_SECRET` | случайный ключ на время процесса |

Приоритет: явно переданный флаг → окружение → default. Явно пустые значения
адресов считаются ошибкой; проверяется только окончательный результат слияния.
Пустой JWT_SECRET, как и отсутствующий, заменяется случайным ключом.
Используется стандартный глобальный `flag.Parse()`: `-h`/`-help` выводят справку
и завершают процесс с кодом 0, ошибочные флаги — с кодом 2. В этих случаях
выход выполняет сам парсер, без defer (включая logger.Sync).
Ошибки валидации конфигурации и запуска возвращают код 1, штатное завершение — 0.
LoadConfig вызывается один раз при старте. Стандартная справка показывает defaults
из окружения, включая DATABASE_URI, который может содержать пароль.

HTTP-адрес — host:port с портом 1–65535; допускаются `:8080`, `localhost:8080`,
`[::1]:8080`. PostgreSQL DSN принимает `postgres://`, `postgresql://` и
keyword/value, например `host=localhost port=5432 dbname=gophermart user=postgres
password=postgres sslmode=disable` (одной строкой).
Accrual — HTTP(S) origin без credentials, префикса пути, query и fragment;
завершающий `/` допустим и удаляется после проверки.

Адреса БД и accrual обязательны. Worker обращается к accrual для незавершённых заказов. Разбор DSN через pgx может учитывать стандартные PG*-переменные
и служебные файлы драйвера. Приложение не записывает DSN в логи.

## Локальный запуск

Из корня репозитория:

```sh
GOTOOLCHAIN=local make build
GOTOOLCHAIN=local make run
GOTOOLCHAIN=local make run RUN_ADDRESS=:8090
GOTOOLCHAIN=local make test
```

Makefile передаёт локальные defaults: HTTP `:8080`, accrual `http://localhost:8081`,
DSN из примера выше. Все параметры переопределяются переменными make.
DSN передаётся одним shell-аргументом, включая пробелы и одиночные кавычки;
команда с DSN не печатается. Для буквального `$` в значении make используйте `$$`
и учитывайте quoting вашей оболочки.

Прямой запуск с URL DSN:

```sh
./cmd/gophermart/gophermart -a :8080 \
  -d 'postgresql://postgres:postgres@localhost:5432/gophermart?sslmode=disable' \
  -r http://localhost:8081
curl -i http://localhost:8080/unknown
```

Ожидается 404. Ctrl+C (SIGINT) или SIGTERM завершает приложение.
ReadHeaderTimeout=5s, ReadTimeout=10s, WriteTimeout=30s, IdleTimeout=60s.
Shutdown получает отдельный контекст на 10s; при истечении соединения закрываются
принудительно и приложение возвращает ошибку. Общий бюджет сервисной операции
HTTP — 25s, начиная после разбора тела. Родительская отмена и более ранний дедлайн
сохраняются. Повторы бизнес-операций БД используют тот же бюджет, не обновляя его на попытках.

## Готовый accrual

Запустите установленный PostgreSQL средствами своей ОС. Например, для
Homebrew: `brew services start postgresql@18`; для другой установки используйте
её службу или `pg_ctl -D /path/to/learning-cluster -l /path/to/postgres.log start`.
Проверьте доступность: `pg_isready -h localhost -p 5432`. Создайте новую учебную БД:
`createdb -h localhost -p 5432 -U postgres gophermart`. Если имя занято, выберите
новое и передайте его в DATABASE_URI; существующие данные не очищайте.
Утилиты PostgreSQL должны находиться в PATH.

Заранее подготовьте PostgreSQL и отдельную учебную БД `gophermart`. Приложения
не создают саму базу. Запускайте в отдельных терминалах:

```sh
GOTOOLCHAIN=local make run-accrual
# Во втором терминале:
GOTOOLCHAIN=local make run
```

`ACCRUAL_RUN_ADDRESS` по умолчанию `:8081`, `ACCRUAL_DATABASE_URI` наследует
`DATABASE_URI`. Пример: `make run-accrual ACCRUAL_RUN_ADDRESS=:8082` и
`make run ACCRUAL_SYSTEM_ADDRESS=http://localhost:8082`.

Цель выбирает существующий бинарник по `go env GOHOSTOS GOHOSTARCH`:
darwin/arm64, darwin/amd64, linux/amd64, windows/amd64. Windows требует GNU Make
и POSIX-оболочку. Неподдерживаемая платформа или отсутствующий файл дают ошибку;
скачивание замены не выполняется. Перед запуском очищаются конфликтующие
`RUN_ADDRESS`, `DATABASE_URI`, `ACCRUAL_SYSTEM_ADDRESS`, чтобы accrual использовал
переданные `-a` и `-d`. Выбранный файл при необходимости получает исполняемый бит.

Проверены выбор локального darwin/arm64, передача DSN в аргументах и запуск HTTP
на заданном адресе при конфликтующем окружении;
на этапе 3 выполнен совместный smoke-запуск с Gophermart в изолированной БД
PostgreSQL 18.6. GET неизвестного заказа вернул 204; Gophermart сохранил данные
и версию схемы. Создания собственных таблиц accrual в этом сценарии не наблюдалось;
на этапе 3 полный цикл записи/начисления не проверялся; результаты этапа 6 приведены ниже.

## Структура после ревью каркаса

`main` создаёт zap, вызывает `config.LoadConfig()`, затем
`build.BuildApp(cfg, logger)` из `internal/build` и `App.Run(ctx)`.
Он логирует ошибки и штатную остановку, выполняет Sync до выхода.

`BuildApp` вызывает ServerBuilder.Build и передаёт готовый *http.Server в App.
App.Run управляет запуском и остановкой готовых сервера и worker, не собирая зависимости.
Конкретный билдер в `internal/server` хранит chi и адрес, принимает готовые
handler-структуры через `AddHandler(method, path, handler) error` и создаёт
`*http.Server`. В BuildApp зарегистрированы два публичных маршрута авторизации. AddHandler проверяет метод, непустой путь
с `/` и обычный nil; повторная регистрация заменяет обработчик. Полный синтаксис
шаблонов оставлен chi, типизированный nil не проверяется.

Общий `internal/interfaces.Logger` предоставляет Debug/Info/Warn/Error с zap.Field.
`LoadConfig()` самостоятельно читает окружение и аргументы процесса, после чего
вызывает отдельный `Validator`. Ошибки различимы через errors.Is и оборачиваются
названиями действий. Проверки выполняются последовательно до первой ошибки.

## Подключение и миграции

База существует заранее; роль приложения должна иметь право создавать объекты
в `public`. Пул: максимум 10 открытых и 5 свободных соединений, срок жизни 30 минут,
простой 5 минут. Стартовый Ping получает 5 секунд; прикладных повторов нет.
При ошибке подключения или миграций HTTP не запускается, ресурсы освобождаются.
При остановке БД закрывается после завершения HTTP-запросов и worker.

`internal/build.BuildApp` отдельным шагом вызывает DBStorageBuilder.Build.
Конструктор билдера получает DSN, источник миграций и готовый interfaces.Retryer. Билдер создаёт и настраивает
sql.DB, выполняет Ping и миграции, затем возвращает DBStorage с готовым пулом.
При ошибке билдер закрывает пул сам. После успешной сборки пул принадлежит storage.
App получает свой интерфейс только с Close и вызывает его после завершения HTTP,
в том числе при ошибке открытия listener. Сервер собирается в BuildApp до
подготовки storage: ошибка его сборки не оставляет открытого пула БД.

Операции AddUser и FindUserByLogin реализованы методами DBStorage. Сервис получает
общий internal/interfaces.DBStorage, который повторяет методы storage, кроме Close.
AddUser создаёт пользователя и нулевой баланс одной транзакцией Read Committed;
возвращает пользователя только после успешного Commit. Конфликт конкретного
ограничения логина даёт ErrLoginTaken, остальные SQL-ошибки остаются внутренними.
Повторяется целая транзакция только для разрешённых ошибок. Неизвестный исход
регистрации не повторяется; ошибки Rollback сохраняются через errors.Join.
sql.DB и sql.Tx не передаются сервисам или HTTP-обработчикам.

Сигнатура BuildApp сохранена: подготовка БД выполняется с context.Background до
App.Run и регистрации сигналов в main. Действуют прежние таймауты Ping и SQL
миграций; прикладных повторов нет.

Пять пар SQL в корневом `migrations` встроены через go:embed и не зависят
от рабочего каталога. Таблицы: `public.gophermart_users`, `gophermart_balances`,
`gophermart_orders`, `gophermart_withdrawals`. Служебная таблица —
`public.gophermart_schema_migrations`; повторный Up с ErrNoChange штатен.
Каждый SQL-файл выполняется в своей транзакции BEGIN/COMMIT.

Выделенное миграционное соединение использует statement_timeout=30s,
lock_timeout=5s. Старые значения сохраняются и восстанавливаются до возврата
соединения в пул. При ошибке миграции или восстановления физическое соединение
исключается из пула: на нём могут остаться транзакция или advisory lock.
Сам пул закрывает только App. Up библиотеки не принимает context: отмена во время
Up ожидает завершения SQL с серверными таймаутами, после чего HTTP не запускается.
Это предел отдельного SQL, а не общий дедлайн всех миграций.

Ошибки БД возвращаются без специальной фильтрации текста драйвера. Ошибка
подготовки и ошибка закрытия пула объединяются через errors.Join. Бизнес-операции используют общий retryer;
подготовка пула и миграции не входят в её область.

## Ручная проверка на отдельной учебной БД

Первый/повторный запуск, ограничения, dirty и lock_timeout проверены на
изолированном PostgreSQL 18.6; полный протокол и ограничения находятся в
docs/IMPLEMENTATION-STATUS.md. SQL-моки сами по себе не доказывают корректность
DDL, ограничений или блокировок.

1. Запустить приложение на новой учебной БД и выполнить
   `SELECT version, dirty FROM public.gophermart_schema_migrations;`:
   ожидаются `5, false` и четыре прикладные таблицы.
2. Повторить запуск с контрольными учебными данными: они должны сохраниться.
   Запустить собранный бинарник из другого каталога.
3. Проверить UNIQUE/FK/CHECK, регистрозависимость логинов Alice/alice,
   каскадное удаление только специально созданного пользователя и индексы
   сортировки. Подробный список — docs/STAGE-03-SCHEMA.sql.
4. На той же учебной БД запустить готовый accrual и проверить, что оба приложения
   работают без конфликтов имён. Один префикс таблиц этого не доказывает.
5. Сбой DDL, dirty-состояние и ожидание блокировки проверять только в одноразовой
   БД. При dirty остановить приложение, установить фактическое состояние схемы,
   исправить причину и вручную согласовать версию с фактической схемой.
   Приложение никогда не выполняет автоматические Down, Force или Drop.

Для осознанного ручного отката **только отдельной тестовой БД** можно использовать
закреплённую CLI-версию. Откат удаляет данные соответствующих таблиц; команды ниже
приведены как инструкция и агентом не выполнялись:

```sh
GOTOOLCHAIN=local go install -tags postgres github.com/golang-migrate/migrate/v4/cmd/migrate@v4.20.1
migrate -path migrations -database 'postgresql://USER:PASSWORD@HOST:PORT/TEST_DB?sslmode=disable&search_path=public&x-migrations-table=gophermart_schema_migrations' down 1
```

CLI принимает URL DSN, а не keyword/value. Проверки 4→3→4 и полного цикла отката
остаются ручными; не применяйте этот шаблон к пользовательской БД.


## Регистрация и вход

`JWT_SECRET` — обычная строка минимум 32 байта: пробелы не обрезаются, Base64
не декодируется. Непустое значение короче 32 байт останавливает запуск.
При отсутствующем или пустом значении LoadConfig получает 32 случайных байта через
crypto/rand и сохраняет их в Config.JWTSecret. BuildApp использует готовый ключ. Ключ не записывается в файл/БД; после перезапуска с новым временным
ключом прежние токены недействительны. Флаг для секрета не добавлен.

Логин и пароль — непустые строки, без нормализации регистра и пробелов; Alice и
alice различны, строки из пробелов допустимы. Для хранения пароля используется
согласованный учебный MD5 в lowercase hex, без соли. Это учебное ограничение,
не рекомендация для защиты реальных паролей.

```sh
curl -i -X POST http://localhost:8080/api/user/register \
  -H 'Content-Type: application/json' \
  --data '{"login":"student","password":"learning-password"}'

curl -i -X POST http://localhost:8080/api/user/login \
  -H 'Content-Type: application/json' \
  --data '{"login":"student","password":"learning-password"}'
```

Успех — 200 с пустым телом и `Authorization: Bearer <JWT>` в заголовке ответа.
Клиент передаёт полное значение этого заголовка в последующих защищённых запросах.
Cookies, refresh, logout и JSON-тело с токеном не используются.

JWT HS256 действует час. Claims содержат только sub (ID), iat и exp. Проверяются
подпись, алгоритм, обязательные claims, положительный int64 ID, время выпуска и
истечения; при now >= exp токен отвергается без допуска по времени.

Тело читается как один JSON-объект независимо от Content-Type, неизвестные поля
игнорируются, хвост из пробельных символов разрешён. Повторные поля сохраняют
стандартное поведение encoding/json. Общий лимит тела — 64 КиБ; превышение,
повреждённый JSON, второе значение, неверные типы, отсутствующие/null/пустые
обязательные поля дают 400. Собственные ограничения длины полей не вводятся.

| Сценарий | HTTP | Тело ошибки (с переводом строки) |
| --- | --- | --- |
| Неверный запрос | 400 | invalid request |
| Логин занят при регистрации | 409 | login already taken |
| Неверная пара логин/пароль | 401 | invalid credentials |
| Сбой БД или подписи | 500 | internal server error |

Authorization выставляется только при успехе. Внутренние детали, пароль, хеш и
токен не включаются в ошибки и диагностику обработчиков. Если подпись не удалась
после Commit регистрации, пользователь сохраняется и может войти позже.

`middleware.Auth` подключён через Wrap к маршрутам заказов и баланса. Middleware принимает ровно одно значение Authorization
с двумя компонентами через пробелы/табуляцию и схемой Bearer без учёта регистра.
При отказе отвечает 401 unauthorized, при успехе передаёт ID через `requestcontext.User`.
Он не обращается к БД и не обновляет токен.

Исторические проверки этапа 4: юнит-тесты с race, go vet, сборка; тогдашнее покрытие 85,9%.
На отдельном PostgreSQL проверены регистрация, нулевой баланс, вход, конфликт,
конкурентная регистрация (200/409, один пользователь и баланс), сбой БД → 500.
Фактические команды, артефакты и непроверенные пункты записаны в
`docs/IMPLEMENTATION-STATUS.md`. Полные бизнес-автотесты и CI ещё не запускались.


## Размещение HTTP-компонентов и тестов

- `internal/handler/register.go`: `Register`, конструктор `NewRegister`;
  `login.go`: `Login`, конструктор `NewLogin`. Каждая структура реализует ServeHTTP.
- `internal/handler/interfaces.go`: общий контракт AuthService для обоих обработчиков;
  его мок — `interfaces_mock_test.go`, пакет `handler_test`.
- `internal/middleware/auth.go`: `Auth` и локальный TokenVerifier;
  тесты `auth_test.go`, мок `auth_mock_test.go`, пакет `middleware_test`.
- `internal/dto/credentials.go`: `Credentials.Decode(io.Reader)` разбирает JSON.
  Лимит HTTP-тела, ответы и бюджет операции остаются в handler.
- `internal/requestcontext/user.go`: `User` с WithID/ID для middleware и будущих обработчиков.
- Мок общего DBStorage находится в `internal/interfaces/mock/storage_mock.go`,
  пакет `mock`; его импортируют тесты сервисов.

Тесты соответствуют файлам структур и проверяют публичный API из внешних пакетов
`handler_test`, `middleware_test`, `dto_test`, `requestcontext_test`, `service_test`.
Приватные методы отдельно не тестируются. Генерация закреплена на mockgen v0.6.0.
Приведённые выше 85,9% относятся к проверке этапа 4 до этого рефакторинга;
актуальное измерение этапа 6 записано в docs/IMPLEMENTATION-STATUS.md.


## Загрузка и список заказов

Оба маршрута требуют `Authorization: Bearer <JWT>` из регистрации или входа.
Middleware проверяет токен без БД. Сервис проверяет существование пользователя:
удалённый пользователь получает 401, ошибка БД — 500. Владелец берётся только
из контекста авторизации, параметры query/body не позволяют его изменить.

```sh
curl -i -X POST http://localhost:8080/api/user/orders \
  -H "Authorization: Bearer $TOKEN" --data-binary '12345678903'
curl -i http://localhost:8080/api/user/orders \
  -H "Authorization: Bearer $TOKEN"
```

POST читает текст независимо от Content-Type, обрезает только внешние пробельные
символы. Дополнительного лимита тела нет. Номер состоит из ASCII-цифр, проходит
Луна и не имеет ведущих нулей, кроме одиночного 0. Номер не преобразуется в int64.
TEXT UNIQUE сохраняет физическое ограничение PostgreSQL на размер ключа индекса;
ошибка хранения такого номера возвращается как 500.

| Сценарий POST | HTTP | Тело ошибки |
| --- | --- | --- |
| Новый заказ | 202 | пустое |
| Повтор своего заказа | 200 | пустое |
| Чужой заказ | 409 | order already belongs to another user |
| Пустой номер / ошибка чтения | 400 | invalid request |
| Неверный номер | 422 | invalid order number |
| Нет авторизации / пользователя | 401 | unauthorized |
| Внутренняя ошибка | 500 | internal server error |

Ошибки — text/plain с завершающим переводом строки. JWT не обновляется.
Заказ создаётся как NEW, accrual=NULL, время задаёт PostgreSQL. Повтор сохраняет
время, статус и начисление. Внешний accrual при загрузке не вызывается.

GET возвращает 204 с пустым телом для пустого списка или 200 application/json
с массивом собственных заказов от новых к старым; при равном времени — ID DESC.
Поля: number, status, uploaded_at (UTC RFC3339), accrual при ненулевом указателе.
Внутренние ID не возвращаются. Начисление хранится в сотых int64 и форматируется
точно, без float64. Для NEW/PROCESSING с nil поле отсутствует; итоговый ноль
возвращается числом. Итоговые статусы устанавливает обработка начислений.

Сервис — internal/service/order.go. Преобразователь — internal/service/mapper.Order,
транспортные данные — internal/dto.Order. Отдельные обработчики UploadOrder и
ListOrders используют общий handler.OrderService. SQL остаётся в DBStorage.

PostgreSQL 18.6 прошли. Историческое покрытие на завершение этапа 5 — 89,0%, включая cmd/build/migrations

## Начисления и баланс

BuildApp настраивает пять попыток бизнес-операции БД, включая первую, с паузами
1/2/4/8 секунд и пределом отдельной задержки 10s. Повторяются SQLSTATE 40001 и
40P01; отмена прекращает серию. Ping и миграции не используют эту политику.
Неизвестный исход записи разрешает повтор только для идемпотентной операции и
при разрешении стратегии; сетевые ошибки в исходную стратегию не входят.

Worker сразу выбирает все NEW/PROCESSING по id ASC, освобождает rows и
последовательно запрашивает accrual общим HTTP-клиентом с таймаутом 10s.
После прохода, пустой выборки или ошибки БД он ждёт 1s. У фоновых SQL-операций
нет отдельного таймаута: используется контекст остановки. 429 приостанавливает
всю очередь и повторяет тот же заказ; Retry-After — секунды, fallback 20s.
Повторяющийся 429 может удерживать очередь на одном заказе. 204, временный сбой
и некорректный ответ сохраняют состояние и допускают следующий заказ.

Начисление применяется в Read Committed с порядком блокировок баланс → заказ.
Конечный статус защищает от повторного начисления; current и статус меняются
атомарно, withdrawn не меняется. Числа разбираются без float64 и округляются до
сотых вверх при третьей цифре от 5. INVALID и PROCESSED без начисления сохраняют 0.
GET /api/user/balance возвращает точные числа current и withdrawn, включая нули.

При остановке отменяются worker и контексты HTTP. Shutdown имеет бюджет 10s;
после принудительного закрытия соединений App всё равно ждёт завершения
обработчиков и worker, прежде чем закрыть БД. Произвольный обработчик, который
игнорирует отмену, может продлить это ожидание.

Историческая проверка этапа 6: полный цикл готового accrual на отдельной БД PostgreSQL 18.6. Подготовка
товаров/заказов использовала API из [официальных примеров поставщика](https://github.com/Yandex-Practicum/go-autotests/blob/main/cmd/gophermarttest/accrual_suite_test.go):
POST /api/goods и POST /api/orders. Проверены точное начисление 12.35, ноль,
сохранность и возобновление после перезапуска. Подробный протокол и ограничения
проверок находятся в docs/IMPLEMENTATION-STATUS.md.

## Универсальные повторы после ревью этапа 6

Механизм находится в internal/service/retry.Retryer. Он получает интерфейс
Strategy.Next(failedAttempt, err) (time.Duration, bool) и выполняет
Do(ctx, func() error) error. При отказе стратегии или исчерпании попыток
возвращается последняя ошибка операции. Ожидание — select time.After/ctx.Done;
отдельного Waiter нет. Отмена и PermanentError запрещают повтор независимо
от стратегии; errors.Is/As сохраняются.

Стратегии находятся в internal/service/retry/strategy. BuildApp внедряет в
DBStorage общий retryer с Exponential/SQLState, а в accrual.Client — такой же
retryer с RateLimit. У HTTP-клиента нет собственного цикла повторов. Каждый
HTTP-запрос заново создаётся и полностью закрывается до паузы. 429 повторяется
в клиенте, поэтому последовательный worker не переходит к следующему заказу.
204/500/некорректные ответы возвращаются вызывающему коду. Worker сохраняет
только периодический опрос очереди с интервалом 1s; его проход не оборачивается
дополнительным retryer. Сервис начисления не повторяет Fetch при SQL-retry.

Прежние postgres.Client/RetryPolicy и обе реализации ContextWaiter удалены.
SQL-транзакции и ограничение повторов неизвестного исхода записи сохранены.


## Списание и история

POST /api/user/balance/withdraw и GET /api/user/withdrawals защищены тем же Bearer JWT.
Пример списания: `{"order":"2377225624","sum":30}`. Положительная сумма должна точно
представляться в сотых int64: 12.34 и 12.340 равны; 12.345 отклоняется без округления.
Структурные ошибки JSON дают 400, ограничения суммы и неверный номер — 422.
Номер проверяется по Луну без обрезания пробелов; тело ограничено 64 КиБ.

Новое списание и повтор того же номера/пользователя/суммы возвращают 200 с пустым
телом. Повтор не меняет баланс и историю, в том числе при уменьшенном остатке.
Другой владелец или сумма дают 409, недостаток средств — 402. Номера списаний
и загруженных заказов независимы. История содержит только order, sum, processed_at,
сортируется по времени и внутреннему ID убывающе; время UTC RFC3339. Пустая история — 204.

Read Committed и блокировка баланса сериализуют начисления и списания. История,
current и withdrawn меняются атомарно; переполнение withdrawn откатывает операцию
и возвращает 500. Общий бюджет сервисной HTTP-операции — 25 секунд со всеми повторами.
Неизвестный исход Commit допускает повтор только при разрешении стратегии;
начальная SQLState-стратегия сетевые ошибки не повторяет.

DTO внешнего accrual находится в internal/dto.AccrualResponse. Правила его числового
разбора и повторов сохранены; наружу клиент возвращает бизнес-модель AccrualResult.
Проверки этапа 7 и границы подтверждённого результата описаны в docs/IMPLEMENTATION-STATUS.md.

## Учебные ограничения

Поддерживается один экземпляр приложения с одним последовательным worker.
Поддержка нескольких одновременно работающих worker-экземпляров не заявлена.
MD5 без соли выбран только для учебного проекта. TEXT UNIQUE ограничен
физическим размером индексного ключа PostgreSQL. Gzip, Docker Compose и собственный
постоянный интеграционный набор не добавлены. SQL-моки и race detector не
доказывают транзакционные гарантии PostgreSQL: их проверяют отдельной ручной
приёмкой и внешними автотестами. Исторические результаты выше не заменяют
протокол проверки текущего дерева в docs/ACCEPTANCE.md.
